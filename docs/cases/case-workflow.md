# Как готовить и публиковать кейсы Марии

Рабочий порядок, собранный 21 октября 2026 года по кейсу «Рабочее место мясника». Использовать вместе с [правилами кейсов](README.md) и [брифом следующего кейса](case-brief-template.md).

## Что мы сделали на примере «Мясорубки»

1. **Проверили контекст и источники.** Прочитали правила личного сайта, нашли проект «Сайт компании» IT Production и проверили его документацию. Отдельного fact sheet «Мясорубки» там не обнаружили; исходную фактуру нашли в материалах личного сайта и дополнили прямым рассказом Марии. Отсутствие источника обозначили, а не заполнили предположениями.
2. **Выделили личную продуктовую работу.** Из интервью восстановили цепочку: клиент упомянул отрицательные остатки и себестоимость → Мария разобрала процесс → обнаружила вечерний ввод данных о разрубе → предложила ввод на рабочем месте → создала прототип → сопровождала разработку и тестирование → передала решение компании на внедрение. Разработку отделили от личного вклада.
3. **Собрали историю решения.** Основной конфликт: товар уже продаётся, но его поступление ещё не отражено в учёте. Кейс объясняет причину, изменение процесса и пользу для управления сетью.
4. **Разложили историю по визуальным блокам.** Hero с фото магазина; реконструкция диалога; схема исходного процесса; шесть проблем с иконками; новое решение и галерея трёх интерфейсов; эффекты; личный вклад; вопросы руководителей; приглашение на встречу. Отдельный блок дашбордов убрали по редакционному решению Марии.
5. **Собрали локальный прототип.** Отдельная Astro-страница, меню и подвал как на главной, адаптивная вёрстка, перелистывание и увеличение скриншотов, воспроизведение диалога, простые анимации с `prefers-reduced-motion`.
6. **Отредактировали тексты и анонс.** Заменили заглушку на главной реальным интерфейсом, коротким описанием, сравнением «было → стало», подтверждённым результатом и кнопкой «Как я решила задачу». Убирали повторы между заголовком, описанием и подписями.
7. **Подготовили SEO.** Выбрали тему автоматизации рабочего места мясника, описательный URL, title/description, canonical, социальное превью, Article/BreadcrumbList, тематические вопросы и включение страницы в sitemap. Контроль потерь раскрыли через проверку расхождений, без утверждения о доказанном снижении краж.
8. **Проверили и опубликовали.** Выполнили сборку и технические проверки, проверили экранные размеры, затем после отдельного подтверждения Марии создали commit, отправили его в GitHub и дождались успешного GitHub Pages. На основном домене проверили доступность, индексацию, sitemap, canonical и переход с главной.

**Результат:** [опубликованный кейс](https://maria-galieva.ru/cases/avtomatizaciya-rabochego-mesta-myasnika/), [анонс на главной](https://maria-galieva.ru/#cases). Выпуск: commit `68af312`, [публикация GitHub Pages](https://github.com/Mymediim/maria-galieva-site/actions/runs/39637669103). Детали семантики: [SEO-карта](myasorubka-seo.md).

Возврат статичного hero и обработка фотографии блока заявки были сопутствующими правками сайта. Они не являются обязательными этапами подготовки нового кейса.

## Порядок для следующего кейса

### 1. Собрать фактуру и определить границы публикации

- Найти материалы проекта, действующий fact sheet, предыдущие тексты, макеты и рабочие интерфейсы.
- Записать источник и дату подтверждения каждого существенного факта. Если документа нет, собрать краткий fact sheet из ответов Марии.
- Установить: исходный запрос, реальная проблема, ограничения, личные решения Марии, работа команды, статус продукта и подтверждённый результат.
- Проверить возможность публикации названия клиента, изображений, отзывов и данных. Предоставление материала для кейса не означает разрешение показывать любые сведения на нём.
- Не придумывать сроки, бюджет, экономию, продажи, ROI и эффекты, которых нет в источниках.

**Готовность этапа:** понятно, что известно, что требует уточнения и какой личный эпизод составляет основу истории.

### 2. Выбрать главный смысл и структуру

Сформулировать одной фразой: какую проблему бизнеса помогла решить Мария и какое её решение заслуживает разбора.

Базовая цепочка: **ситуация → исследование → причина → выбор решения → реализация → результат**. Состав страницы подбирать по материалу, не копировать все блоки «Мясорубки» автоматически.

Для каждого блока определить сообщение и подходящий формат:

| Содержание | Формат |
| --- | --- |
| Контекст и итог | Hero + короткие сведения о роли |
| Как заметили проблему | Эпизод интервью или реконструкция диалога |
| Причина в процессе | Схема «до», линия времени, сравнение |
| Выбор Марии | Короткое обоснование решения или сравнение вариантов |
| Реализация | Реальные интерфейсы с подписями и галереей |
| Эффект | Подтверждённые факты и показатели с источником |
| Личный вклад | Конкретные действия по этапам, отдельно работа команды |
| Вопросы будущего клиента | Несколько содержательных ответов |

Реконструкцию разговора обозначать как реконструкцию. Макет не называть работающим продуктом, а возможность продукта — измеренным эффектом.

### 3. Написать и сократить тексты

- Заголовок объясняет предмет кейса; подзаголовок раскрывает проблему и решение.
- «Я» относится к подтверждённым действиям Марии; работа разработчиков и клиента приписывается им.
- Подписи объясняют, что делает пользователь и зачем это нужно бизнесу.
- Убрать одинаковые мысли из соседних блоков и абстракции без примеров.
- Не использовать «автоматизировали всё» как универсальный вывод для следующих кейсов: уточнять реальные границы автоматизации.
- CTA связывать с похожей задачей посетителя и вести на существующую запись на встречу.

### 4. Собрать страницу и анонс в существующем проекте

- Работать в Astro и стиле личного сайта. Не применять автоматически стиль IT Production.
- Сохранить общую шапку, меню, подвал, согласие на аналитику и работу на телефоне.
- Чередовать схемы, интерфейсы и короткие тексты. Тёмный блок использовать для смыслового акцента; не затемнять каждый второй блок механически.
- Изображения хранить локально, оптимизировать, задавать `alt`, размеры и lazy loading ниже первого экрана. Оригиналы сохранять отдельно.
- Простые анимации не должны скрывать содержание без JavaScript или мешать чтению; учитывать уменьшение движения.
- На главной дать короткий самостоятельный анонс: клиент/задача, визуальное доказательство, проблема и решение, подтверждённый результат, переход в кейс. Не дублировать весь рассказ со страницы.

### 5. Подготовить SEO до выпуска

- Определить язык и намерение будущего клиента, основной запрос и близкие задачи. Выдача помогает понять контекст, но не доказывает частотность и не гарантирует позиции.
- Сразу выбрать стабильный описательный URL с дефисами. После смены URL обновить страницу, все внутренние ссылки, canonical, структурированные данные, sitemap и проверки. Для уже опубликованного адреса отдельно предусмотреть редирект с учётом возможностей хостинга.
- Настроить уникальные title/description, один H1, canonical, Open Graph/Twitter и подходящие структурированные данные без выдуманных дат и результатов.
- Поисковые формулировки включать в полезный читателю текст, не собирать из них повторяющийся перечень.
- Добавить страницу в sitemap только для открытой production-сборки. Локальный и тестовый просмотр оставлять закрытыми.
- Подключить существующий компонент аналитики с согласием и события переходов/заявок.

### 6. Проверить конкретный выпуск

Из корня проекта:

```powershell
npm run check
npm run build
npm run verify:images
npm run verify:analytics:configured
```

Открытую SEO-сборку проверять с `PUBLIC_SITE_URL=https://maria-galieva.ru` и `PUBLIC_SITE_INDEXING=true`: после сборки выполнить `npm run verify:seo:open`. Отдельно собрать закрытый вариант с `PUBLIC_SITE_INDEXING=false` и выполнить `npm run verify:seo:closed`. Переменные задавать только для процесса проверки; локальный `.env` не публиковать и не выводить.

Важный текущий нюанс: `verify-seo-build.mjs` и `verify-production-launch.mjs` знают адрес кейса «Мясорубка» и ожидают два адреса в sitemap. При добавлении следующей страницы расширить проверяемый набор страниц и ожидаемый sitemap, сохранив проверки ранее выпущенных страниц. Не менять проверки просто ради зелёного результата.

В браузере проверить:

- компьютер, планшет и телефон, включая 320 px; переносы длинных слов и отсутствие горизонтального переполнения;
- меню, CTA, переход с главной, галерею, увеличение, диалог и FAQ, если они есть;
- загрузку изображений, контраст на светлых и тёмных фонах, уменьшение движения;
- отсутствие ошибок JavaScript, корректную работу согласия на аналитику;
- фактически публикуемую сборку, а не только dev-прототип.

При автоматических скриншотах дождаться загрузки lazy-изображений и завершения анимаций. Dev toolbar не относится к продукту и может попадать в технические селекторы.

### 7. Согласовать и опубликовать

1. Показать готовый результат и точный состав выпуска; проверить Git diff и отсутствие секретов, временных файлов и посторонних черновиков.
2. Получить разрешение Марии на commit, отправку в GitHub, публикацию и открытую индексацию. Не запрашивать повторно в пределах уже согласованного выпуска.
3. Создать commit только с проверенными файлами. Отправка в `main` запускает существующие CI и GitHub Pages; не делать push до разрешения.
4. Дождаться успешных проверки и deploy именно для отправленного commit. Успешный push ещё не означает публикацию.
5. Выполнить `npm run verify:production`; проверить страницу и переход на основном домене. Записать URL, commit, запуск deploy и результат проверки.
6. Обновить память проекта. Запрос переобхода в поисковых кабинетах выполнять как отдельное согласованное действие; открытая индексация не означает немедленное появление в выдаче.

Если рядом есть несогласованные изменения, изолировать выпуск или точечно включить нужные изменения, не удаляя чужую работу. Не восстанавливать всю главную из старого commit ради одного блока.
