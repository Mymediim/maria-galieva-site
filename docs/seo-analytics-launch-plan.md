# SEO-аудит и задача на запуск индексации и аналитики

Дата аудита: 18 сентября 2026 года

Основной домен: `https://maria-galieva.ru`

Язык и рынок: русский, услуги для собственников и руководителей малого и среднего бизнеса
Роль сайта: личный экспертный лендинг с записью на бесплатную встречу

## 1. Цель этапа

Подготовить сайт к безопасному открытию для поисковых роботов и к измеримому запуску:

- Google и Яндекс могут обойти и проиндексировать основную страницу;
- поисковые системы получают один канонический адрес, валидные метаданные и sitemap;
- Яндекс Метрика и Google Analytics 4 загружаются только после согласия посетителя;
- измеряются клики по основным целевым действиям;
- изображения не создают чрезмерную нагрузку на мобильную загрузку;
- запуск проверяется в production, а не только по исходному коду.

Цель этапа не включает обещание позиций, трафика или появления в AI-ответах. Базовая техническая готовность лишь делает сайт доступным для обхода и измерения.

## 2. Проверенный baseline

### Статус реализации на 18 сентября 2026 года

- Локально реализованы согласованные SEO-сигналы для закрытого и открытого режимов: meta robots, `robots.txt`, валидный sitemap, canonical и автоматические проверки сборки.
- Юридические страницы переведены в `noindex, follow` и исключены из sitemap.
- Добавлены `ProfilePage` → `Person`, расширенные Open Graph/Twitter-метаданные и отдельное изображение 1200×630.
- Используемые изображения оптимизированы: проверяемый общий объём — около 190 КиБ; размеры, lazy loading и приоритет hero заданы явно.
- Реализованы согласие на аналитику, повторное открытие настроек и события CTA для Метрики и GA4.
- Оба идентификатора аналитики проверены по формату и добавлены в GitHub Variables; workflows получают их без записи в репозиторий.
- Мария подтвердила открытие индексации и публикацию версии с аналитикой. Production workflow переведён в открытый режим; итоговый статус фиксируется после завершения deploy и проверки опубликованных ответов.
- Настройка русского домена и подключение панелей вебмастеров остаются отдельными действиями.

### 2.1. Что уже сделано хорошо

- Главная, политика и пользовательское соглашение отвечают `200 OK` по HTTPS.
- `http://maria-galieva.ru/` и `https://www.maria-galieva.ru/` перенаправляются кодом `301` на `https://maria-galieva.ru/`.
- На главной один `h1`, последовательная структура `h2`–`h4`, русский `lang="ru"`.
- Есть уникальные `title` и `description`, абсолютный canonical, Open Graph, favicon.
- На главной присутствует JSON-LD сущности `Person` с привязкой к IT Production.
- Основной контент доступен в HTML без необходимости выполнять JavaScript.
- Баннер согласия не загружает внешнюю аналитику до выбора посетителя.
- Политика обработки персональных данных упоминает Яндекс Метрику и Google Analytics.
- Неизвестный URL возвращает `404`.

### 2.2. Блокеры запуска индексации

| Факт | Текущее состояние | Риск |
|---|---|---|
| `robots.txt` | `User-agent: *` + `Disallow: /` | Роботам запрещён обход всего сайта. |
| Meta robots | На всех HTML-страницах `noindex, nofollow` | Страницы явно запрещены для индексации. |
| Sitemap | Возвращает `200 OK`, но вместо XML содержит текст `Sitemap is disabled before production launch.` | Формально доступен невалидный sitemap; его нельзя отправлять в панели вебмастеров. |
| Русский домен | `мария-галиева.рф` возвращает временный `302` на парковку Timeweb; корректного HTTPS нет | Поисковая система и пользователь попадают не на сайт Марии; возникает конкурирующий брендовый адрес. |
| Вебмастеры | В DNS нет TXT-подтверждений Google/Yandex, в HTML нет verification-тегов | Нет подтверждённого доступа к Search Console и Яндекс Вебмастеру. |

### 2.3. Аналитика

| Факт | Текущее состояние | Вывод |
|---|---|---|
| Локальный `.env` | Имена переменных правильные, но значениями служат целые HTML-фрагменты счётчиков | Компонент ожидает только числовой ID Метрики и ID вида `G-...`; локальные значения невалидны. |
| `.env.example` | В репозитории также сохранены полные фрагменты кода | Пример нужно заменить безопасными понятными заглушками. |
| GitHub Variables / Secrets | Не настроены | Production-сборка не получает идентификаторы. |
| Workflow | Передаёт URL и `PUBLIC_SITE_INDEXING=false`, но не передаёт ID аналитики | На опубликованной странице оба ID пустые. |
| Production | Код загрузчиков присутствует, но из-за пустых ID запросы к счётчикам не запускаются | Сейчас посещения не собираются даже после согласия. |
| Целевые действия | Явные события для календаря, Telegram, кейсов и IT Production не реализованы | После подключения будут видны просмотры, но воронка останется неполной. |
| Управление согласием | Есть первичный выбор, но повторно открыть настройки можно только очисткой localStorage | Нужна видимая ссылка «Настройки аналитики» и возможность изменить решение. |

Идентификаторы Метрики и GA4 являются публичными идентификаторами сайта, а не паролями. Их можно хранить в GitHub Variables. API-ключи, пароли и токены туда переносить нельзя.

### 2.4. Производительность и изображения

- На главной загружается 8 растровых изображений общим исходным весом **6,32 МиБ**.
- Два фото весят примерно по 1,7–1,8 МиБ.
- Два логотипа весят примерно 0,9 и 1,34 МиБ; один исходник логотипа имеет размер 3400×700.
- Ни у одного из 8 изображений нет HTML-атрибутов `width` и `height`.
- Ни у одного изображения нет `loading="lazy"`; изображения ниже первого экрана загружаются сразу.
- У hero-изображения нет явного `fetchpriority="high"`.
- Полевых Core Web Vitals пока нет: сайт новый. Запрос PageSpeed Insights во время аудита не вернул результат, поэтому баллы не предполагались.

Это главный технический риск скорости. Ориентиры после оптимизации: LCP ≤ 2,5 секунды, INP ≤ 200 мс и CLS ≤ 0,1 на 75-м перцентиле реальных загрузок.

### 2.5. Метаданные и сущность эксперта

- Title главной — 39 символов, description — 142 символа: базовый размер корректный.
- Canonical абсолютный и указывает на HTTPS без `www`.
- Для главной есть `Person`, но для страницы личного эксперта понятнее использовать `ProfilePage` с `mainEntity: Person` и устойчивым `@id`.
- Не хватает `og:site_name`, `og:image:width`, `og:image:height`, `og:image:alt`, а также явных Twitter title/description/image.
- Текущее OG-изображение — обычное портретное фото 1355×1160 и весом около 1,78 МиБ. Нужен отдельный лёгкий social preview 1200×630.

### 2.6. Контентная база

Для брендового запуска лендинг достаточен: он объясняет специализацию, задачи, подход, услуги, стоимость и содержит кейс. Для устойчивого продвижения по разным коммерческим и информационным намерениям одного URL мало.

Следующие смысловые кластеры уже видны в содержании:

1. продуктовый консультант / проектирование цифрового продукта;
2. проектирование сайта до разработки;
3. проектирование мобильного приложения и состава MVP;
4. разбор бизнес-процесса перед автоматизацией;
5. ИИ для руководителя и практическая работа с ИИ;
6. брендовые запросы «Мария Галиева» и «Мария Галиева IT Production».

Не нужно создавать массовые однотипные SEO-страницы. После запуска полезнее подготовить самостоятельные содержательные страницы услуг, полные кейсы и авторские разборы с подтверждённой фактурой.

## 3. Задача на проработку

### Итерация 1. Техническая готовность и скорость — P0

#### 1.1. Исправить конфигурацию окружения

- В `.env` оставить только чистые значения:
  - `PUBLIC_YANDEX_METRIKA_ID` — только цифры;
  - `PUBLIC_GA_ID` — только идентификатор вида `G-...`;
  - `PUBLIC_SITE_URL=https://maria-galieva.ru`;
  - `PUBLIC_SITE_INDEXING=false` до финального разрешения.
- Очистить `.env.example` от реальных фрагментов счётчиков и оставить заглушки.
- Добавить публичные ID в GitHub Variables, не в исходный код и не в GitHub Secrets.
- Передать Variables в `ci.yml` и `deploy.yml`.

Критерий приёмки: production HTML содержит валидные непустые ID, но до согласия браузер не запрашивает домены Метрики и Google Analytics.

#### 1.2. Оптимизировать изображения

- Подготовить WebP/AVIF или оптимизированный WebP для двух фотографий и тяжёлых логотипов.
- Для hero использовать подходящий размер под фактический контейнер и отдельные варианты для мобильного/desktop при необходимости.
- Добавить `width` и `height` всем изображениям.
- Hero: `fetchpriority="high"`, без lazy loading.
- Фото встречи и логотипы ниже первого экрана: `loading="lazy"` и `decoding="async"`.
- Отдельно создать social preview 1200×630 разумного веса.

Целевой критерий: используемые изображения заметно легче текущих 6,32 МиБ; исходный бюджет — до 1,5 МиБ на все изображения страницы и до 300 КиБ на LCP-изображение. Финальный критерий — лабораторный LCP ≤ 2,5 с и отсутствие заметного CLS.

#### 1.3. Исправить индексирующую сборку

- При `PUBLIC_SITE_INDEXING=true`:
  - главная получает `index, follow`;
  - `robots.txt` возвращает `200`, разрешает обход и содержит абсолютную ссылку на sitemap;
  - `sitemap.xml` возвращает валидный XML с `200`.
- Политику и пользовательское соглашение оставить доступными по ссылкам, но рассмотреть `noindex, follow` и исключение из sitemap: они не являются целевыми страницами поиска.
- Когда индексация выключена, sitemap не должен публиковаться как `200 application/xml` с произвольным текстом. Для статического GitHub Pages проще собирать валидный sitemap только для production-режима и не ссылаться на него в закрытом robots.txt.
- Добавить автоматические проверки собранного `dist`: robots, sitemap, canonical, meta robots и отсутствие тестового URL.

Критерий приёмки: после тестовой production-сборки XML проходит парсинг, в sitemap только канонические индексируемые URL, а переключатель индексации меняет все связанные сигналы согласованно.

#### 1.4. Канонизация доменов

- Сохранить существующие постоянные `301` с HTTP и `www` на `https://maria-galieva.ru/`.
- Для `мария-галиева.рф` выпустить бесплатный SSL и настроить постоянный `301` на соответствующий URL основного домена.
- Не индексировать парковочную страницу и не использовать временный `302` как финальное решение.

Критерий приёмки: все четыре варианта — HTTP/HTTPS, `www`, русский домен — приводят к основному HTTPS-адресу без цепочек и ошибок сертификата.

### Итерация 2. Аналитика и измеримая воронка — P0

#### 2.1. Подключить счётчики после согласия

- Сохранить текущий принцип: внешние скрипты не загружаются до согласия.
- Проверить загрузку Яндекс Метрики и GA4 на главной, политике и соглашении.
- Не включать Вебвизор без отдельного решения по правовым основаниям и политике обработки данных.
- Добавить в футер ссылку «Настройки аналитики», позволяющую повторно открыть выбор, отозвать или дать согласие.

Критерий приёмки:

- до согласия нет запросов к `mc.yandex.ru` и `googletagmanager.com`;
- после согласия оба запроса появляются один раз;
- после отказа они не появляются;
- решение сохраняется и может быть изменено пользователем.

#### 2.2. Настроить события

Единые события для обоих счётчиков:

| Событие | Когда отправлять | Параметры |
|---|---|---|
| `calendar_click` | Клик на запись в Google Calendar | `placement`: `hero`, `meeting`, `services`, `footer` |
| `telegram_click` | Клик на Telegram | `placement`: `hero`, `meeting`, `footer` |
| `it_production_click` | Переход на сайт компании | `placement`: `method`, `cases`, `footer` |
| `case_click` | Переход к опубликованному кейсу | `case_name` |
| `analytics_consent_granted` | После согласия и загрузки счётчиков | без персональных данных |

Событие отказа не отправлять во внешнюю аналитику: до согласия аналитические системы не должны загружаться.

Критерий приёмки: каждое событие видно в режиме отладки/реального времени Метрики и GA4 ровно один раз на клик, без URL с персональными данными.

#### 2.3. Настроить цели и базовый отчёт

- В Яндекс Метрике создать цели для `calendar_click`, `telegram_click`, `case_click`.
- В GA4 отметить `calendar_click` и `telegram_click` как ключевые события.
- Зафиксировать стартовую дату и нулевой baseline.
- Минимальный ежемесячный отчёт: пользователи, каналы, поисковые запросы из вебмастеров, устройства, CTA-клики, доля кликов по CTA от посетителей с согласием.
- Реальные записи сверять с календарём вручную: внешний календарь не подтверждает сайту завершённое бронирование.

### Итерация 3. Открытие индексации — P0/P1

#### 3.1. Улучшить метаданные и структурированные данные

- Оставить один `h1`, текущий title и description использовать как исходную версию.
- Преобразовать JSON-LD в `ProfilePage` → `mainEntity: Person`, добавить стабильный `@id`, основное изображение и подтверждённые `sameAs`.
- Добавить полный набор Open Graph/Twitter для главной и social preview 1200×630.
- Проверить JSON-LD валидатором Schema.org и Rich Results Test. Наличие разметки не означает гарантированный расширенный результат.

#### 3.2. Подключить панели вебмастеров

- Создать Domain property `maria-galieva.ru` в Google Search Console и подтвердить через DNS TXT.
- Добавить `https://maria-galieva.ru/` в Яндекс Вебмастер и подтвердить права через DNS, HTML-файл или meta-tag.
- После открытия индексации отправить `https://maria-galieva.ru/sitemap.xml` в обе системы.
- Запросить проверку главной страницы и убедиться, что она доступна для индексирования.

Критерий приёмки: права подтверждены, sitemap принят без ошибок, URL Inspection/«Проверка страницы» не показывает запрета robots/noindex.

#### 3.3. Финальный переключатель

Только после прохождения всех P0 и отдельного подтверждения Марии:

- установить `PUBLIC_SITE_INDEXING=true` в production workflow;
- собрать и опубликовать сайт;
- проверить production-ответы, не полагаясь только на локальную сборку;
- отправить sitemap и запросить обход главной.

Критерий приёмки production:

- `/` → `200`, `index, follow`, корректный canonical;
- `/robots.txt` → `200`, обход разрешён, указан sitemap;
- `/sitemap.xml` → `200`, валидный XML с каноническими URL;
- HTTP и `www` → один `301` на основной HTTPS;
- русский домен → постоянный `301` на основной HTTPS;
- счётчики не загружаются до согласия и работают после него;
- `npm run check` и `npm run build` проходят;
- нет ошибок консоли на desktop и mobile;
- выполнена повторная проверка PageSpeed/Lighthouse.

## 4. P1 после запуска

- Через 3–7 дней проверить первый обход, ошибки покрытия и реальные события аналитики.
- Через 2 недели проверить индексирование в Яндекс Вебмастере и Search Console; это контроль, а не обещание срока включения в поиск.
- Подготовить отдельные страницы услуг только после карты запросов и подтверждения содержания.
- Выпустить полный кейс «Рабочее место мясника» с интерфейсами, ролью, результатом и разрешёнными подтверждениями.
- Сформировать редакционный план авторских материалов под реальные вопросы собственников, а не под массовые вариации ключей.

## 5. Что потребуется от Марии

1. Подтвердить использование найденных идентификаторов Яндекс Метрики и GA4 либо дать правильные чистые ID без HTML-кода.
2. Подтвердить, что аналитику можно включить после текущего механизма согласия и текста политики; при необходимости получить юридическую проверку трансграничной передачи данных для GA4.
3. Разрешить настройку постоянного редиректа и бесплатного SSL для `мария-галиева.рф`.
4. Авторизовать добавление сайта в Google Search Console и Яндекс Вебмастер либо самостоятельно создать ресурсы и передать коды подтверждения.
5. Отдельно подтвердить момент открытия индексации после приёмки P0.
